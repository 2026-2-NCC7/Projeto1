2. Funcionalidade 1 — Motor de Matching Heurístico Explicável

2.1. User Story e Critérios de Aceite

  • Como recrutador da área de tecnologia,
  • Quero calcular um índice de aderência explicável entre o perfil do candidato e os requisitos da vaga,
  • Para tomar decisões de triagem fundamentadas em dados auditáveis, sem caixas-pretas e sem penalizar injustamente competências não avaliadas.

Critérios de Aceite:

  1. A pontuação deve seguir a fórmula ponderada:

\text{MATCH} = (w_{hard} \cdot \text{HARD}) + (w_{soft} \cdot \text{SOFT}) + (w_{exp} \cdot \text{EXP}) + (w_{cond} \cdot \text{COND})

  1. A soma dos pesos configurados deve ser validada rigorosamente para totalizar 1.0.
  2. Nenhuma competência classificada como NAO_AVALIADA pode receber nota 0 arbitrariamente; deve-se atribuir crédito basal e sinalizar a pendência.
  3. Todos os números mágicos de alinhamento e penalidades devem ser expressos por constantes nomeadas com semântica clara.

2.2. Code Smells Identificados (Antes da Refatoração)

  • Primitive Obsession (Obsessão por Primitivos): Os 4 pesos eram números de ponto flutuante soltos, sem validação estrutural de consistência no domínio.
  • Magic Numbers (Números Mágicos): Valores como 0.50, 0.35, 0.25, 1.25, 40.0 e 50.0 estavam espalhados pelo código sem justificativa semântica explícita.
  • Violação do Princípio da Responsabilidade Única (SRP): O cálculo matemático de pontuação ponderada estava acoplado diretamente dentro da montagem do payload HTTP e da persistência de banco de dados.
  • *Aviso de Descontinuação (Deprecation Warning):* Uso de datetime.utcnow(), gerando advertências no Python 3.12/3.13.

    def __init__(self, ..., weights: Optional[MatchingWeights] = None):
        if weights is not None:
            weights.validate()
            self.weights = weights
        else:
            self.weights = MatchingWeights(...)
        self.w_hard = self.weights.hard_skills
        ...

    def compute_overall_score(self, hard_score: float, soft_score: float, exp_score: float, conditions_score: float) -> float:
        """Função pura com Princípio da Responsabilidade Única (SRP)."""

3. Funcionalidade 2 — Verificador de Evidências Literais (Verbatim)

3.1. User Story e Critérios de Aceite

  • Como candidato e auditor do sistema,
  • Quero que as citações atribuídas às minhas competências sejam auditadas programaticamente contra minhas respostas reais,
  • Para ter certeza de que o modelo de linguagem não inventou dados, experiências ou falas que não proferi.

Critérios de Aceite:

  1. A correspondência deve ser categorizada em níveis tipados (EXACT, CASE_INSENSITIVE, NORMALIZED_LENIENT, REJECTED).
  2. Cada resultado deve fornecer um índice numérico de confiança entre 0.0 e 1.0.
  3. Chamadas legadas esperando desempacotamento de tupla (is_valid, detail = verify_quote(...)) devem continuar funcionando sem quebrar contratos existentes (100% retrocompatível).
  4. Suporte a verificação em lote (batch processing) para otimizar validações em entrevistas com dezenas de perguntas.

3.2. Code Smells Identificados (Antes da Refatoração)

  • Output Truncation / Poor Information: O verificador retornava apenas uma tupla booleana simples (bool, str), sem discriminar a qualidade da evidência ou o grau de normalização aplicada.
  • Inflexibilidade para Auditoria: Não era possível saber programaticamente se uma citação foi literal de primeiro nível ou se exigiu remoção de acentos para ser localizada.
  • Falta de Abstração de Domínio: O resultado de validação era um tipo primitivo sem métodos próprios ou semântica rica.

# DEPOIS:
class MatchType(str, Enum):
    EXACT = "EXACT"
    CASE_INSENSITIVE = "CASE_INSENSITIVE"
    NORMALIZED_LENIENT = "NORMALIZED_LENIENT"
    REJECTED = "REJECTED"

@dataclass(frozen=True)
class VerificationResult:
    is_valid: bool
    detail: str
    match_type: MatchType
    confidence_score: float

    def __iter__(self):
        """Permite desempacotamento retrocompatível: is_valid, detail = result."""
        yield self.is_valid
        yield self.detail

class EvidenceVerifier:
    @classmethod
    def verify_quote(cls, quote: str, transcript_or_answer: str) -> VerificationResult:
        if quote_clean in transcript_clean:
            return VerificationResult(True, quote_clean, MatchType.EXACT, 1.0)
        if quote_clean.lower() in transcript_clean.lower():
            return VerificationResult(True, verbatim_in_text, MatchType.CASE_INSENSITIVE, 0.95)
        if len(quote_lenient) >= 15 and quote_lenient in transcript_lenient:
            return VerificationResult(True, f"Correspondência normalizada: '{quote_clean}'", MatchType.NORMALIZED_LENIENT, 0.85)
        return VerificationResult(False, "Citação não localizada...", MatchType.REJECTED, 0.0)

Este documento formaliza a especificação técnica, hiperparâmetros, limitações e protocolo experimental dos modelos de Machine Learning e Processamento de Linguagem Natural (NLP) integrados na versão 1.0 do Q.I. Tech Matchmaker Engine.

1. Arquitetura dos Modelos e Especificações Técnicas

A solução adota uma arquitetura híbrida de três modelos especializados, cada um desacoplado com responsabilidades bem delimitadas, evitando o uso de modelos monolíticos generalistas como "caixa-preta".

Componente Modelo Provedor / Framework Parâmetros Hardware Alvo Papel no Sistema
Modelo 1: Transcrição de Áudio faster-whisper-small CTranslate2 / faster-whisper ~244M CPU (int8) Reconhecimento automático de fala (ASR), geração de timestamps e transcrição em pt-BR.
Modelo 2: Extração de Competências qwen3:4b Ollama (Local) ~4B CPU / GPU Local Extração de evidências, classificação de profundidade fática e estruturação em JSON Schema.
Modelo 3: Representação Semântica intfloat/multilingual-e5-small Sentence Transformers / PyTorch ~118M (384d) CPU Vetorização densa de competências e sinônimos com prefixos assimétricos (query: / passage:).

2. Detalhamento dos Componentes

2.1. Modelo 1 — Reconhecimento e Transcrição de Fala (faster-whisper)

  • Técnica de Otimização: Quantização int8 através do runtime CTranslate2, reduzindo o consumo de memória RAM de ~1 GB para menos de 350 MB e acelerando a inferência em processadores comuns de usuário (x86_64).
  • Parâmetros de Inferência:
  • beam_size: 5
  • language: pt (Português do Brasil)
  • vad_filter: True (Silero VAD integrado com tolerância de silêncio de 500 ms para eliminar ruídos de fundo).
  • Rastreabilidade e Governança: O sistema mantém o áudio original em diretório configurável com política de retenção (AUDIO_RETENTION_DAYS) e armazena o texto bruto (raw_text) de forma imutável, permitindo ao candidato revisar e corrigir o texto antes do envio (edited_text).

2.2. Modelo 2 — Extração Fática de Competências (qwen3:4b via Ollama)

  • Modo de Operação: Inferência estruturada local com garantia de formato JSON Schema via endpoint /api/chat.
  • Temperatura: 0.1 (baixa dispersão para assegurar reprodutibilidade e evitar alucinações criativas).
  • Tamanho de Janela de Contexto: 4096 tokens.
  • Mitigação de Prompt Injection (Cenário G): As respostas dos candidatos são tratadas estritamente como dados não confiáveis inseridos entre delimitadores rígidos ([RESPOSTA id="..."] """conteudo""" [FIM RESPOSTA]). O metaprompt de sistema proíbe categoricamente a execução de instruções contidas nas transcrições.
  • Validação Programática Rigorosa (EvidenceVerifier): Nenhuma citação textual (exact_quote) é persistida sem que o backend confirme que o trecho existe ipsis litteris ou sob normalização de espaços no texto da transcrição. Citações não localizadas são sumariamente descartadas.
  • Modo de Contingência (Fallback): Na ausência de GPU ou do Ollama em execução local, o motor aciona o extrator determinístico baseado em padrões semânticos e casamento de termos da taxonomia, assegurando que o sistema opere continuamente.

2.3. Modelo 3 — Representações Semânticas (multilingual-e5-small)

  • Estrutura Vetorial: Modelo de 12 camadas Transformer baseado em XLM-RoBERTa, produzindo vetores de dimensão D = 384.
  • Protocolo Assimétrico de Entrada:
  • Para requisitos e consultas: prefixo obrigatório "query: ".
  • Para competências e trechos textuais: prefixo obrigatório "passage: ".
  • Métrica de Similaridade: Similaridade Cosseno sobre vetores normalizados L_2:

\text{sim}(u, v) = \frac{u \cdot v}{\|u\|_2 \|v\|_2}

  • Salvaguarda Explicável: A similaridade cosseno é utilizada exclusivamente para normalização terminológica (mapeamento de sinônimos como "Py" \rightarrow "Python" ou "K8s" \rightarrow "Kubernetes"), nunca sendo interpretada isoladamente como probabilidade de aptidão ou garantia de contratação.

3. Formulação do Algoritmo de Matching Explicável

Em contraste com algoritmos "caixa-preta", o cálculo do índice de compatibilidade é totalmente auditável e baseado em rubricas determinísticas:

\text{MATCH} = (w_{\text{hard}} \cdot S_{\text{hard}}) + (w_{\text{soft}} \cdot S_{\text{soft}}) + (w_{\text{exp}} \cdot S_{\text{exp}}) + (w_{\text{cond}} \cdot S_{\text{cond}})

Valores padrão configuráveis:

  • w_{\text{hard}} = 0.50 (Hard Skills)
  • w_{\text{soft}} = 0.25 (Soft Skills)
  • w_{\text{exp}} = 0.15 (Anos de Experiência Relevante)
  • w_{\text{cond}} = 0.10 (Condições Objetivas: CLT/PJ, Remoto/Presencial, Pretensão Salarial)

Cobertura de Avaliação

O sistema calcula independentemente a métrica de Cobertura da Avaliação:

\text{COBERTURA} = \frac{N_{\text{requisitos avaliados na entrevista}}}{N_{\text{total de requisitos da vaga}}} \times 100\%

Requisitos obrigatórios não abordados na entrevista são categorizados como PENDENTE_AVALIACAO, alertando o recrutador sobre a necessidade de aprofundamento específico em vez de penalizar o candidato de forma arbitrária com nota zero.

4. Protocolo Experimental para Avaliação Acadêmica Rigorosa

Para a validação formal em bancas acadêmicas (TCC/Mestrado) e artigos científicos, recomenda-se a execução dos seguintes ensaios empíricos:

4.1. Métricas de Extração de Competências (NLP)

A partir de um dataset de teste anotado por 3 especialistas humanos independentes (Double-Blind Annotation com cálculo de concordância via Cohen's Kappa ou Fleiss' Kappa \kappa > 0.75):

  • Precisão (Precision): \frac{TP}{TP + FP} — Proporção de competências identificadas pelo modelo que eram reais.
  • Revocação (Recall): \frac{TP}{TP + FN} — Proporção de competências presentes nas falas que foram capturadas.
  • F1-Score: 2 \times \frac{P \times R}{P + R} — Média harmônica.
  • Fidelidade da Evidência (Evidence Fidelity): Proporção de citações literais verificadas com sucesso pelo EvidenceVerifier sem descarte por alucinação.

4.2. Métricas de Transcrição Fonética (ASR)

  • Word Error Rate (WER):

\text{WER} = \frac{S + D + I}{N}

Onde S são substituições, D deleções, I inserções e N o total de palavras da referência humana, medindo robustez contra sotaques regionais brasileiros.

4.3. Métricas de Ranking (Information Retrieval)

Comparação do ranking gerado pelo Matchmaker Engine com o ranking consolidado de recrutadores técnicos sêniores:

  • NDCG@k (Normalized Discounted Cumulative Gain): Avalia a qualidade da ordenação dos candidatos nos primeiros k lugares.
  • MRR (Mean Reciprocal Rank): Recíproco da posição do primeiro candidato considerado altamente qualificado pela banca.

5. Limitações Atuais e Próximos Passos de Pesquisa

  1. Ajuste Fino Supervisionado (Supervised Fine-Tuning - SFT): Treinar adaptadores LoRA/QLoRA sobre o modelo Qwen com corpus anotado de entrevistas técnicas em língua portuguesa.
  2. Treinamento por Contrastive Learning: Ajustar o modelo multilingual-e5-small utilizando Triplet Loss com âncoras de requisitos técnicos, exemplos positivos (descrições reais equivalentes) e exemplos negativos (competências homônimas ou de áreas distintas).
  3. Escalabilidade Vetorial: Migração da abstração em memória para PostgreSQL com extensão pgvector utilizando índices HNSW (Hierarchical Navigable Small World) com produto escalar normalizado.
  4. Proteção Contínua contra Vieses: Auditoria periódica de disparidade de impacto (Disparate Impact Ratio) para garantir conformidade ética e regulatória (Marco Legal da IA e LGPD).

1. Visão Geral

O Q.I. Tech Matchmaker Engine é uma plataforma inteligente projetada para transformar a triagem de talentos em tecnologia. O sistema analisa três fontes principais de dados:

  1. Informações autodeclaradas pelo candidato (níveis 1 a 5 e preferências).
  2. Evidências textuais concretas extraídas de entrevistas de triagem por áudio ou texto.
  3. Requisitos técnicos e comportamentais estruturados cadastrados pelas empresas.

O Grande Diferencial: Explicabilidade Baseada em Evidências

Ao contrário de soluções genéricas que delegam a avaliação a um chatbot ou produzem percentuais opacos, o motor Q.I. Tech:

  • Exige comprovação fática: Associa competências a citações literais e verificadas do candidato.
  • Distingue estados epistêmicos: Classifica em EVIDENCIADA, PARCIALMENTE_EVIDENCIADA, EVIDENCIA_INSUFICIENTE, NAO_AVALIADA ou DIVERGENCIA_IDENTIFICADA.
  • Garante o Direito de Réplica: O candidato pode contestar análises específicas, gerando uma nova versão do relatório (v1 \rightarrow v2) sem destruir o histórico.
  • Fórmula de Compatibilidade Explicável: Ponderação determinística de 4 dimensões (Hard Skills, Soft Skills, Experiência, Condições Objetivas) com cálculo explícito da Cobertura de Avaliação.

8. Integração com a Plataforma Q.I. Tech (Node.js / NestJS)

O motor foi construído como um serviço independente (Microservice Architecture), expondo endpoints RESTful documentados no padrão OpenAPI 3.0.

Exemplo de Integração em NestJS

typescript
import { Injectable } from '@nestjs/common';
import { HttpService } from '@nestjs/axios';
import { firstValueFrom } from 'rxjs';

@Injectable()
export class MatchmakerService {
  constructor(private readonly http: HttpService) {}

  private readonly engineUrl = 'http://localhost:8000/api/v1';

  async runJobMatching(jobId: string) {
    const response = await firstValueFrom(
      this.http.post(`${this.engineUrl}/matching/jobs/${jobId}/run`)
    );
    return response.data; // Retorna ranking, pontuação explicável e justificativas
  }

  async getCandidateReport(candidateId: string) {
    const response = await firstValueFrom(
      this.http.get(`${this.engineUrl}/candidates/${candidateId}/latest-report`)
    );
    return response.data; // Retorna competências autodeclaradas vs evidenciadas
  }
}

9. Privacidade, LGPD e Diretrizes Éticas

  • Bases Legais: Registro obrigatório de consentimento (consent_records) e finalidade de triagem técnica.
  • Não-discriminação: Nenhuma característica pessoal protegida (gênero, idade, raça, endereço, sotaque) é enviada aos modelos ou utilizada em cálculos de compatibilidade.
  • Decisão Humana Final: O sistema opera como ferramenta de assistência analítica (Human-in-the-Loop), rejeitando explicitamente a eliminação 100% automatizada de candidatos.
